## 1. Did the separation appear? (Stop-list 2 — the sentence this report owes)

**Structurally, yes — and it is the *only* place it appears. In wall-clock, no:
at $n \le 5$ the compact arm shows the *smallest* EK win of the three arms, not
the largest.**

That is one finding stated in two halves, and the halves point in opposite
directions, so both are spelled out below rather than averaged into a verdict.

**The structural separation holds, exactly as Phase 3 pinned it.** Arm 3's
$A_N$ is $14 + 2n$ top-level conjuncts — logarithmic in $N$ — while the DFA it
denotes has $\Theta(N^2)$ states. Measured here at $n = 2 \ldots 5$:
$\lvert\mathrm{DFA}(A_N \to \gamma_N)\rvert = 17, 65, 257, 1025 = N^2 + 1$,
**byte-identical across all three arms and both goals**. Arms 1 and 2 reach the
same DFA from a formula of $14N + 2n$ resp. $14N + 2N$ conjuncts — polynomial in
the formula size. So arm 3 is superpolynomial in $\lvert A_N \rvert$ and arms
1, 2 are not. Stop-list 2's trigger ("binary-compact tracks binary-enumerated")
**did not fire**.

**The wall-clock separation did not appear.** The EK-over-no-knowledge speedup at
the largest $n$ measured:

| arm | $\lvert A_N\rvert$ | EK-vs-nk speedup at $n=5$ ($N=32$) |
|---|---|---|
| 1 `slippery-binary` (enumerated) | $14N + 2n$ | **212×** |
| 3 `slippery-binary-compact` (compact) | $\mathbf{14 + 2n}$ | **2.1×** |
| 2 `slippery-onehot` (enumerated) | $14N + 2N$ | 9.4× *(at $n=3$, its cap)* |

The arm carrying the exponential structural separation is the arm where
externalizing the knowledge buys the least. The mechanism is visible in the
numbers and is not subtle: **Spot's translation cost tracks the size of the
formula, not the size of the DFA it denotes.** Both binary arms build the same
$1025$-state DFA at $n=5$; the enumerated arm needs $10\,702$ ms to get there
from a $14N + 2n$-conjunct formula, the compact arm $106$ ms from a $14 + 2n$-conjunct
one. Writing $A_N$ compactly is itself worth ~100×, and it captures most of what
externalizing it into a $\Tin$ would have bought.

**What this does and does not license.** It does not touch the D8 assertions —
they are about automaton *sizes* and they hold. It does bear on the PRD's
framing that "arms 1 vs 3 isolate compactness … this is where the separation
must appear": the separation appears there structurally and **inverts** there
dynamically. Whether that reframes idea 1's headline is a theory call, not a
benchmark call, and it is left for the evening (see §7 Q1). **Nothing was
adjusted, re-scoped or re-run to make this come out differently.**

## 7. Questions for the evening grill

**Q1 (the big one) — does §1 reframe idea 1's claim?** The compact $A_N$ is the
encoding the PRD was built to vindicate, and it *does* separate structurally. But
it is also the encoding for which externalizing into a $\Tin$ buys almost nothing
in wall-clock (2.1× at $N=32$), because Spot's translation tracks formula size.
The measured EK win is largest exactly where the assumption was written badly.
Two readings, and picking between them is yours: (a) the claim is about
*translation blow-up* and the right baseline is a user who authors $A_N$ naively,
so 212× is the honest number; (b) the claim should be stated against the *best*
monolithic encoding available, in which case the honest number is 2.1× and the
paper's framing needs to change. This is O5-class and was not decided here.

**Q2 — the extractor column's measurement frame is accidental.** Flagged by the
code review. The dict handed to `dependent_inputs` already carries
`register_turn_order_aps`' full variable order (every $\Ifree$ var pinned above
every controllable), which the shipped `ltlf-ek-deps` binary never has. BDD
variable order can move this wall-clock by a large factor. D9 pins the entry
point as "the same core `ltlf-ek-deps` drives" **and** claims the column is
"directly comparable to Tuesday's corpus sweep" — under this dict that
comparability is **not established**, so §4.3's break-even $k$ should not yet be
quoted against Tuesday's numbers. Two defensible choices, both one-line: *tool
parity* (fresh dict, matching `ltlf-ek-deps`) or *race parity* (same turn-order
dict as the `-nk` column it sits beside). Today it is neither by intent.

**Q3 — should the sweep be re-run Release?** Everything above is Debug (`-O0`,
assertions live), which is why §4.5 disclaims the `ltlfsynt` comparison. Release
would make that column meaningful and would likely move several `TIMEOUT` cells
into range. The plan's baseline note says *do not* configure Release because two
death tests go red — but those two are a documented build-type artifact
(`assert()` compiled out, `tests/bench_test.cpp:412`), not a regression. Running
the *benchmark* Release while testing Debug is a coherent policy; it is just not
the one written down.

**Q4 — min or median?** §6.3. One of the two PRDs should give way.

**Q5 — the budget.** This run's `--budget=5400` truncated run 1 (§3). If the
sweep is meant to be re-runnable in one pass, the PRD's 7200 s is roughly right
for these caps but leaves no margin: the four runs totalled ~9200 s of measured
wall-clock. Worth pinning a per-family budget, or splitting the sweep in the PRD
the way §3 had to split it in practice.

## 8. Findings

**Must-fix, found and fixed during the run:**

1. **The extractor subject silently poisoned a cross-method oracle.** Registering
   `dependent-inputs-extraction` into `bench_subjects()` added **14 red cells** to
   `BenchSuiteCrossMethodAgreement` (7 T1 families × $n \in \{2,3\}$, all at
   `realizable=1`): the test walks `bench_subjects()` unfiltered and reads each
   subject's verdict via a `RealizabilityVerdict(rows)` helper that maps "rows
   present, no `controller_states` row" to *unrealizable*. A cost-measuring
   subject synthesizes nothing, so it read as dissenting everywhere.
   **This hid behind an unchanged `ctest` count** — it is one ctest *test* either
   way, so 699/700 stayed 699/700 and the first developer pass reported green in
   good faith. Caught by the test-writer reading the failure body. Fixed by
   excluding the subject from that loop, following the exclusion the same loop
   already uses for `nfa-product`/`slippery-onehot`; the `BenchSubject` interface
   and the `RealizabilityVerdict` heuristic were **not** touched (both belong to
   `benchmark-suite.md`'s frozen interfaces).
2. Two doc-level must-fixes from `/code-reviewer`: a `bdd_dict`-lifetime claim in
   the new `NkCase::dict` comment that was false in both of its two clauses, and
   a `tests/bench_suite_test.cpp` header invariant ("never asserts on a span
   duration") that the new tests falsified. Both fixed as **comments only** — no
   executable code changed after the sweep ran, so the committed source is
   byte-identical to the binary that produced §4.

**`consider`, recorded and not acted on** (now in the PRD's *Developer comments*):
the extractor's dict frame (§7 Q2); the exclusion in finding 1 is a hardcoded
name inside an otherwise-generic loop, so the *next* non-synthesizing subject

pin is unobservable to the four new tests (the subject discards the result, so a
later narrowing to `c.phi` would not be caught); a `BenchTimer` spelling nit; and
that a `FAILED_*` in the extractor column can mean "degenerate formula" (I11's

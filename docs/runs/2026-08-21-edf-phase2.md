## 3. Findings

### F1 — `slippery-onehot` at $n = 4$ dies of `std::bad_alloc` building $A_N$

The T1 sweep tried $n = 4$ as a fast-conditional extra. `slippery-binary` at
$n = 4$ certifies in ~1.6 s per goal; `slippery-onehot` at $n = 4$ throws
`std::bad_alloc` constructing the DFA of its 32-AP $A_N$ and was dropped from
the test.

This is the same wall as Phase 1's F1 (`NfaProduct` on one-hot at $n = 3$),
one level earlier in the pipeline: it is now the **assumption formula's own
DFA**, not any method's product, that cannot be built. It is PRD **Stop-list 8**
("one-hot dying at large $n$ is a reportable data point, not a bug to tune
around"), and it sharpens Phase 4's expectation — the one-hot arm will not
merely be slow at $n \ge 4$, it will be *absent*, and the sweep's own
`--timeout` will never even see it because the failure is an allocation, not a
deadline. Worth deciding, in the evening, whether Phase 4 should cap the one-hot
arm at $n = 3$ by construction rather than discovering this per cell.

### F2 — the new oracles add ~220 s to every `ctest` run

`slippery-onehot` at $n = 3$ costs ~110 s per goal inside the T1 sweep. The
coverage is what the PRD asks for at $n = 2,3$, so it was kept rather than
weakened, and nothing here is wrong — but the repo's default `ctest` is now
noticeably slower for everyone, permanently. Whether that belongs behind an
opt-in (the `LTLF_EK_SOAK` precedent) is a user call, not a day-run's.

## 4. Review

**Domain (`/code-reviewer`) + theory (`/theory-reviewer`, spawned by it on the
product-construction diff): no `code-bug`.** Two `must-fix`, both documentation,
both applied in `31fb6e8`:

1. T6's deviation (below) was argued in a source comment; it belongs in the
   PRD's *Developer comments*, and now is.
2. The header and the PRD's pinned behaviour #1 said "a missing edge on
   **either** side is an implicit rejecting sink". Only $\tau$'s side gets a
   synthetic sink; `ltlf_to_dfa` is total, so a gap on $\psi$'s side is a
   precondition violation that throws. The theory-reviewer classified this
   `doc-bug`, low severity. The **prose** was corrected; the code's behaviour is
   the right one.

**Deferred (`consider`, not acted on, recorded in the PRD):** the PRD's pinned
behaviour #3 says witnesses are enumerated "in `bdd_dict` variable order"; the
implementation orders by `sigma_slices`-then-lexicographic-AP-name. Fully
deterministic either way and test-verified, but the wording and the code do not
say the same thing.

**Two deviations from the PRD as written, both recorded, neither silent:**

- **T6 was built on a reduced one-axis "slippery-line" ($N = 2$)** rather than on
  mutants of the family's own $A_N$, because D5's `Keep`/`Inc` vocabulary lands
  in Phase 3. `/code-reviewer` judged this an **acceptable** realization, not a
  hollowing-out: T1 already exercises the real generator on every registered
  family, so T6's job is only to prove the machinery discriminates on
  genuinely satisfiable too-weak / too-strong mutants — which it does, against
  independent reference walkers.
- **Pinned behaviour #5 ("slices come from `sigma_slices`") did not say what the
  slices feed.** The implementation uses them to order the BFS's letter
  enumeration while walking the **full** $I \cup O$ alphabet regardless of
  `role`. Reviewed against Stop-list 1: this is the *non-narrowing* reading —
  restricting the walk to $\Sigma_0 \cup \Sigma_1$ would blind the certificate
  to exactly the `mv`-guard mutant T6(b) is built to catch.
